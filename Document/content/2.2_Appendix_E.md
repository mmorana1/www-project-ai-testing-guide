## 2.2 Appendix E: AI Threats Mapping to AI Components Vulnerabilities (CVEs & CWEs) 

**AI Penetration Testing Framework: Scoping, CVE/CWE Mapping, and Threat Correlation**

This appendix guides penetration testers on mapping discovered CVEs and CWEs across SAIF components scoped for pen-testing to their corresponding AI-specific targeted threats identified in the threat model. While CVEs identify known vulnerabilities in the underlying technology stack such as libraries, frameworks, and APIs used to build AI systems and applications, CWEs represent the underlying design and implementation weaknesses that make those vulnerabilities possible. Together, CVEs and CWEs enable testers to connect individual software flaws to broader systemic AI risks, showing how exploited CWEs as weaknesses and CVEs as vulnerabilities in the AI Application/System tech stack can propagate into AI-System layers targeted by AI threats such as prompt injection, data poisoning, or model tampering.

**Step 1: Define Scope and Map SAIF Components to the Technology Stack**

Because AI pen tests target live systems, testers must first define the scope: identify which SAIF components are in scope, document their technology stack, and prioritize where to test. In-scope elements typically include components directly involved in the request–response flow such as chat UIs, API backends, orchestration layers, model frameworks (e.g., LangChain, LlamaIndex), vector stores (Redis, Pinecone, Weaviate), and model-serving endpoints. Once scoped, testers map each component to its tech stack, identify relevant CVEs and CWEs, and trace potential exploit paths. This mapping guides focused validation with scanners, SCA tools, and proof-of-concept testing to show how conventional vulnerabilities can directly impact AI model integrity and behavior.

**Step 2: Threat Enumeration and CVE Exploit Path Mapping**

The process of mapping threats to Ai system vulnerabilities starts by identifying known vulnerabilities in AI systems/applications using Software composition analyzers (SCAs) and runtime tools. SCA Tools (e.g., Snyk, Trivy, Dependabot, OWASP Dependency-Check, and GitHub Advanced Security) will flag vulnerable third party software dependencies, while scanners such as Nessus and Nuclei can confirm active CVE exposures in APIs and services. Runtime telemetry and host inspection can also validate which CVEs are exploitable in live environments. These CVEs are then mapped to AI-specific threats (i.e. TA0i-XX threats) outlined in this guide: for example, a FastAPI sanitization flaw (CVE-2022-36067) can be part of a prompt-injection vector (T01-DPIJ), and an Airflow ETL vulnerability (CVE-2022-40127) can lead to data poisoning (T01-DMP) in a RAG pipeline. For each SAIF component in scope, testers review subcomponents, confirm deployed technologies, and run focused tests to find exploitable or unpatched libraries. An example of this mapping is provided the **AI Threat enumeration and CVE exploit path mapping table 2.2.1.**. Identified findings of CVEs with vulnerability scans can be mapped to Ai threats and used to drive AI-specific attack simulations such as prompt injection, model inversion, data poisoning, or runtime DoS to reveal real application impact. Using the AI threats to CVEs mapping table, testers can maintain traceability from vulnerability to AI threats. For instance, Redis in SAIF #4 (Application Layer) vulnerable to CVE-2022-0543 links to threat/risks like data leakage (T01-SID), model disruption (T01-DoSM), and manipulation (T01-MTD). A single Redis compromise can escalate from infrastructure control to model tampering—compromising data integrity, availability, and trust. 

**Step 3: Threat Enumeration and CWE Exploit Path Mapping**

The next recommended step is to perform a AI threat enumeration and CWE exploit-path mapping. This step transforms vulnerability-centric testing into design-level assurance. By classifying findings under CWE categories, the pen tester bridges the gap between patch management and resilient AI architecture. CWE mapping clarifies attacker objectives, expands test coverage beyond isolated CVEs, and guides remediation that strengthens entire system layers rather than individual components. An example of this AI threats to CWEs mapping is in the **AI Threat enumeration and Targeted CWEs mapping table 2.2.2.** The CWE-based table reframes technical flaws as architectural weaknesses, for instance, CWE-20 (Improper Input Validation) exposes weak parsing logic, CWE-276 (Incorrect Default Permissions) reveals insecure defaults in data storage such as S3 buckets, and CWE-345 (Insufficient Verification of Data Authenticity) uncovers trust and integrity flaws in RAG ingestion. This approach helps testers not only find where AI applications break, but also understand why they break and how to redesign them to resist future exploitation by addressing security by design weaknesses documented in the listed CWEs.
